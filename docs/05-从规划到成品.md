# 从当前草案到真实成品｜五阶段路线

**2026-10-08 状态：阶段1产品方向和边界已认可；阶段2已建立52项功能及22个验收场景，等待复核。** 这是一条结果导向的路线，不规定每阶段必须使用固定的工具顺序或研究轮数。

| 阶段 | 任务 | 完成门槛 |
|---|---|---|
| 1. 完整确定需求 | 汇总已讨论内容、开放问题和不可妥协的教育/设备目标 | 用户确认需求基线，关键风险可见 |
| 2. 能力清单与验收 | [52项功能](04-功能与验收追踪.md)、[能力归属](08-能力归属与集成边界.md)、[22个验收场景](09-验收场景与反例.md) | 能直接用于评估成熟游戏的原生覆盖、补缺工作与证据 |
| 3. 寻找成熟游戏 | 从实际可玩的整套游戏出发，深入核查源码、玩法、素材许可、更新与接口 | 经过实证的候选对比、复用比例、代价与最终选型 |
| 4. 最小补缺适配 | 尽量不碰原游戏主体，补任务、审批、授权、奖励事件及必要外部管控能力 | 家庭任务到游戏原生奖励的真正跨端闭环可用 |
| 5. 整合与验收 | 完整需求回归、真实两孩子试用、数据与设备可靠性、发布/备份 | 可靠的成品、已知限制、维护与恢复说明 |

## 三个必须守住的关口

### G1 游戏底座验收
至少确认：可运行、确实好玩、适合低龄、合法复用（包括美术）、在目标平板上可用、可通过插件/接口/小幅修改发放原生奖励。不能仅凭宣传视频或 README 作决定。

### G2 第一个端到端闭环
孩子进入游戏任务页 → 完成现实任务并申请 → 家长手机审批 → 唯一奖励入账 → 宠物有变化。双家长同时批准、反复提交、离线重试、切换孩子均不串账。

### G3 最终家庭验收
真实使用一段时间，孩子可以独立操作，家长能接受日常工作量；奖励经济合理、数据可以备份恢复、成年后可调整内容，不出现隐私与内容安全问题。对跨应用控制的最终需求，如无法实现则提交事实与取舍选项请用户决定，不得静默删去。手表为扩展目标。

## 项目追踪机制

GitHub 仓库记录唯一的目标与重要决策，GitHub Issues 跟踪阶段事项和验证证据；能创建 GitHub Projects 时以看板聚合，不再造另一套权威需求。

正式开发确认后，再结合实际游戏结构评估引入 OpenSpec；不在当前需求阶段强制安装工具。Codex 的任务指令以明确结果、必要边界及验收标准为主。

每轮施工输出：实际完成、关联需求编号、版本/证据、风险与未完成事项。禁止把研究结论误报为已验证的成品功能。
